# WHBypass 首轮排查反思（2026-10-27）

## 结论

国家网络身份认证 1.2.38 的启动闪退解决了。三条手段：掐掉主二进制 `+0x1406b0` 的反调试守卫、
关掉 KSCrash 安装、接管 Mach 异常端口。冷启动三次各存活 30 秒以上，交互正常。

## 四类假象，每一类都花掉了真实时间

### 用 grep 计数当结论

第一轮对照实验得出"短路 checker 让崩溃从 1 次变成 4 次"，据此写了一整段"改 SDK 内部
会触发完整性自检"的推论，还照着这个推论放弃了那条路。实际是 `grep` 同时匹配了
`EXCFAULT type=` 和 `EXCFAULT 第 N 次` 两种行，前后统计口径根本不一致。把口径统一之后，
开与关都是 4 次。

**判定方法**：计数前先把匹配串固定成唯一前缀，并且两侧用同一条命令。

### 把自己的探针当成对方的行为

为了覆盖新起的线程，曾经每 250ms 调一次 `thread_set_exception_ports`。结果日志里出现
"每 6.1 秒一次跳飞、非常规律"，而这正是反复打断主线程造成的。花了很久往"检测 SDK 有
定时器"的方向查。

**判定方法**：规律性本身不是证据。周期性行为先怀疑自己的周期。

### 把库的行为当成检测

看到 `thread_suspend` 每 6 秒被调用 7～8 次、界面卡死、进程随后消失，第一反应是
"SecureUtilityPlus 在冻结我"——icbc 里同类 SDK 就是这个手法。反汇编调用点之后才看到
旁边的字符串是 `KSCrash Exception Handler (Secondary)`：是我自己接住的异常被崩溃上报库
捕获，它按流程挂起全部线程抓现场。

**判定方法**：告警出现时先看调用点的邻接字符串/符号，再谈归因。命名不同的两个库可以表现
得一模一样。

### 对着错误的地址做修复

毒地址 `0xb5a01000` 无法映射，这件事本身做了一轮实验才发现。更早的时候我在二进制里搜
这个常量，64/32/16 位都是 0 次，本该立刻想到"运行时算出来的"，却先去试了停放页。

**判定方法**：常量搜不到就先退一步想它的生成方式，不要直接试补丁。

## 两条有效的做法

### 先做对照，再谈机制

"短路 checker 有没有用"这个问题，正确做法是一轮一个变量、口径一致地数次数。这一条
最后直接推翻了"改 SDK 内部会触发自检"的错误结论，也省掉了后面可能几轮的无效尝试。

### 用最小可验证的补丁定位

把 `+0x1406b0` 入口改成 `ret` 只用两条指令，却一次把跳飞从 4 次降到 1 次。相比之下，
先花时间去理解 `0x134730` 那套表驱动虚拟机，成本高得多、收益不确定。**先用一个
破坏性的最小实验确认"这段代码是不是元凶"，再去读它。**

## 一个仍然没解释的问题

剩下那 1 次跳飞（`pc = 0xb5a07000`、`lr = 0x1`）的发起方没定位到。它的栈帧被压平了，
帧链直接指向 libdispatch，说明发起方没有建栈帧。目前不影响使用，但意味着还有一处判定
在跑。
