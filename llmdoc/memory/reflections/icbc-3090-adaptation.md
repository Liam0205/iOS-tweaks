# ICBC 3.0.90 适配反思

## 时间

2026-05-10

## 完成了什么

将 icbcbypass v1.0.0（基于 ICBC 3.0.80 开发）适配到 ICBC 3.0.90。确认检测向量无变化，修复了登录后 UI 卡顿问题。

## 关键教训

### 1. 框架方法的全局永久阻断会制造隐性性能退化

CALayer 的 `removeAllAnimations` 和 `removeAnimationForKey:` 被时间门控永久阻断后，不仅冻结循环的调用被拦截，正常 App 的动画清理也被一并拦截。动画对象在 CALayer 上累积 → Core Animation GPU 压力升高 → UIButton highlight 动画挂起 → 按钮需 10+ 次点击。

这个问题在 3.0.80 上未被察觉（可能因为 3.0.80 冻结时序不同、或者登录后操作路径未触发足够动画）。3.0.90 的前置集中冻结模式放大了这个缺陷。

**教训**: 当 hook 的目标是系统框架方法（UIKit/QuartzCore）时，永远假设它被 App 自身的正常功能也在使用。阻断策略必须区分攻击流量与正常流量——速率限制优于时间门控。

### 2. 速率限制是对抗持续循环的更优策略

冻结循环的特征是高频突发（间隔 <50ms），而正常 App 调用是孤立的低频事件。基于调用间隔的速率限制可以精确区分两者，不影响正常功能。

时间门控（前 N 秒放行、之后全部阻断）假设冻结循环只在启动早期运行，这个假设在 removeAllAnimations 场景下不成立。

**教训**: 对于持续运行的攻击循环，基于"调用模式"（频率/间隔）的区分比基于"时间窗口"的区分更鲁棒。

### 3. sched_yield() 减轻忙循环 CPU 消耗

semaphore_wait hook 返回 0 后，冻结循环立即再次调用 → CPU 忙循环。加入 `sched_yield()` 让出时间片，使突发调用从前置集中分布到更均匀的模式，降低了约 20% 的 sema_blocked 计数。

**教训**: 在无法消除忙循环的场景下（冻结循环不可控），主动让出 CPU 是低成本的缓解手段。

### 4. 版本适配不等于检测适配

3.0.90 的检测层与 3.0.80 完全一致，但冻结层的时序模式变化暴露了对抗层的隐性缺陷。适配新版本时，不能只检查"是否新增了检测"，还必须验证"现有对抗在新运行时序下是否仍然有效"。

**教训**: 版本适配检查清单应增加"登录后交互流畅性"验证项。

## 待进一步优化

- 用户反馈"感觉好一些了"但未达到完全流畅，可能仍有优化空间
- 速率限制的 50ms 阈值是否需要根据未来版本调整
- 是否存在其他 hook 也有类似的全局阻断问题
