# hsbchkbypass 第 0 轮反思：先校准测量工具，再造探针

日期：2026-10-27。目标：汇丰香港 3.69.12。结论：**未定位根因**，五版探针全部零命中。

## 实际发生了什么

这一轮花了五版探针（0.0.1 → 0.0.5），每版都在补上一版暴露的缺陷：

| 版本 | 加了什么 | 为什么加 |
|---|---|---|
| 0.0.1 | 终止原语 hook + 镜像清单 + 类清单 + 内联 svc 扫描 | 首版 |
| 0.0.2 | 换成 Swift 布尔方法 hook + 心跳 | 扫描太慢，进程活不到扫描结束 |
| 0.0.3 | 心跳 20ms、atexit、全信号处理器 | 心跳粒度太粗，判断不了死亡时刻 |
| 0.0.4 | svc 扫描挪到独立线程 + `memchr` 加速 | 扫描仍然跑不完 |
| 0.0.5 | hook 自检 + `syscall(2)` hook | 突然意识到零命中可能根本不可信 |

最后一个版本才是关键，而它本该是第一个。

## 教训一：零命中的结论必须先自检

"`exit`/`abort`/`kill`/`raise` 全部零命中"这句话，在没做自检之前有两种解释：
被测代码真的没走这些路径，或者 hook 根本没装上。两者在日志上完全一样。

解决办法成本极低：同一个进程里对 `getpid` 装一次 `MSHookFunction`，自己调一次，
打印命中计数。命中 1 次就证明 hook 机制可用，前面那些零命中才有意义。

前四版探针的结论因此都悬空。第五版加了自检并通过后，才能说"不是 hook 失效造成的假阴性"。

aiabypass 的反思里已经记过"hook 装上了但没被调用，和没装上长得一样"，
但当时只说了"要记录调用计数"，没有给出验证 hook 机制本身的办法。
**记录计数只能证明"被调用了"，自检才能证明"能调用到"。**

## 教训二：静态扫描前先看 cryptid

主二进制 `__TEXT` 在磁盘上是加密的（`LC_ENCRYPTION_INFO_64` 的 `cryptid=1`），
所以头两次对着文件扫 svc 得到的"零命中"完全是噪声，不构成任何证据。

这个信息读一个 load command 就能拿到，比写扫描器快得多。**先确认数据源是否可信，
再决定要不要写分析工具。**

顺带一个容易混淆的地方：同一次实验里，主二进制 `cryptid=1`（结论无效），
而它依赖的 9 个框架 `cryptid=0`（结论有效）。两部分证据的可信度不同，
不能合并成一句"扫过了，没有 svc"。

## 教训三：目标是 900ms 就死的进程，工具要按秒来设计

时间预算是这一轮的硬约束。进程从注入到消失不到 900ms，而：

- 遍历 200MB 的段做逐字比较来不及；
- 用 `objc_getClassList` 抢 ObjC 运行时锁会卡死（主线程正在 dyld 里持有那把锁）；
- 心跳粒度必须到 20ms 量级才分得清"哪一步之后没的"。

回头看，0.0.1 版同时在做四件事（清单 + 扫描 + 心跳），任何一件慢都会把进程拖死，
还看不出是谁的责任。**多线程拆开、每步单独留记号**是后面才想到的，
理应一开始就这么写。

## 教训四：frida 不可用要早点试

`frida.spawn` 在这台设备上对所有 App 都返回 `mach task is gone`（包括能正常运行的
汇丰中国）。这意味着"在启动前布好 hook"这条路整个不通。

这个结论只花了五分钟就试出来了，但试之前已经按"可以用 frida"的假设设计了一版方案。
**搭工具链之前先花几分钟验证工具能不能用。**

## 下次的顺序

1. 读目标二进制的 load command（`cryptid`、段布局、是否加密），确定哪些数据可信；
2. 验证计划要用的每个工具（frida spawn、hook、日志通道）各跑一次最小用例；
3. 写探针：先只做"活多久 + 怎么死的"这件事，由浅入深，每步留时间戳；
4. 确认测量结果可信之后，再往上加检测面的观察。
