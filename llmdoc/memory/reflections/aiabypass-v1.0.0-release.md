# aiabypass v1.0.0 发布反思（2026-10-26）

## 结论先说

友邦友享 6.9.33 不再一打开就闪退，App 能正常用；但**越狱判定本身没有被绕过**，是"处分后果被接住"。这是全仓唯一一个以这种方式收尾的 tweak，发布说明和文档都必须保持这个措辞。

## 走过的弯路

### 把自己的代码没跑起来当成"检测变严了"

改 `ADDITIONAL_OBJCFLAGS` 之后做了增量构建，产物缺 `__DATA` 段（88640 字节降到 33888 字节）。装到设备上 App 在 dyld 阶段就退出，构造函数根本没进，表现是"日志文件 0 字节 + 进程不在"。这个现象与我预期的"检测加固"完全一致，于是花了时间往检测方向查。

判定方法：比对本地构建产物的段结构与安装到设备上的文件 md5，再看大小差了一倍多。修法是改开关后一律 `make clean`。

### 被自己的诊断工具骗了一轮

"零 hook 对照命中 0 条"这个结果，当时被当成"越狱基座没有改写 GOT"的证据，并据此写了一段"我们的 hook 才是元凶"的推论。实际上负责把地址映射到模块名的查表函数依赖构造函数里填的模块快照，在快照之前调用一律返回 NULL，所有条目都被判成"不是越狱库"。补上分时点审计后，同一份内存在 `post-logfile` 时 0 条、`post-snapshot` 时 7 条——变的只是解析能力。

判定方法：诊断工具的输出只有在它能正确解析输入时才可信，先喂一个已知答案验证一次。

### 在有明确证据之前就想"还原"

一开始认定 JM 查的就是越狱基座留下的 GOT 痕迹，于是直接按"磁盘值是 0"把 5 个槽清零、把 `dlopen` 槽写回 `dlsym` 的结果。两个错误同时存在：`__got` 槽在运行时该放真实函数地址而不是 0；`dlsym` 返回的正是 systemhook 的地址。App 当场退出。

后来把符号名一个个查出来（`dlopen`、`dlopen_preflight`、`fork`、`posix_spawn`、`vfork`），自解析 `__LINKEDIT` 符号表拿到未被劫持的地址，7 个槽全部还原 —— App 稳定了，但处决次数仍是 2。**数据是对的，假设是错的。**

## 真正有价值的两个教训

### 1. 时间窗比手段重要

判定发生在 tweak 能运行之前时，所有"让检测看不到痕迹"的手段都会失败，而失败表现是"改了但没用"，很容易被误读成"手段不够好"，于是不断换手段。这次换了三种原理完全不同的手段（interpose、冻结线程、还原 GOT），全部无效且无效方式一致，才意识到该怀疑时间窗。

确认方法很朴素：给关键事件打相对构造函数的时间戳。加完之后一眼看到两次处决在 7ms 和 12ms，而 JM 的检查项在我们装好钩子之后才跑。

### 2. 负面结论要带数字

"试过无效"没有复用价值。这次记成"还原 7 个槽后连续三次启动稳定、处决次数仍为 2"、"挂住 `dlsym` 后从启动到首屏稳定调用次数为 0"，才让后来的人能判断结论是否还成立。

## 发布前做的两处清理

- `AIA_DEBUG_LOG` 默认关闭：日志文件写在 App 自己的 `Documents/` 里，`aiabypass.log` 这个名字本身就是痕迹，正式版不该留。
- 统计线程不再启动：它每 5 秒枚举全部线程与端口，纯为排查服务。高频探针曾直接触发系统唤醒限制（`KYHAppStore.wakeups_resource-*.ips`）把 App 弄死。

## 还没验证的假设

两次处决时机固定、手法一致，也可能是 JM 自己的启动防调试自检，在干净设备上同样会发生、由它自己的处理器接住后继续运行。若如此，"接住"恰好还原了原本行为，而不是"绕过"。验证需要一台未越狱的同型号设备，本机做不到。

## 若将来要继续

两条路，都不在 tweak 范围内：

1. 改主程序加载命令顺序，让我们的镜像排在 JM 之前初始化。
2. 定位发起处决的那段 JM 代码并在那里改结果。处决线程栈上留了 6 个可用的 JM 返回地址（`+0x11c4ac`、`+0x11c720`、`+0x15063c`、`+0x15298c`、`+0x16773c`、`+0x180100`、`+0x1818b8`、`+0x1829ac`），可以据此往上找。
