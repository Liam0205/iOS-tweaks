# hsbchkbypass 分析记录

## 目标

让汇丰香港（`hk.com.hsbc.hsbchkmobilebanking`）在越狱设备上正常运行。
当前实测版本 3.69.12（build 125629），可执行文件 `HongKong.app/HongKong`（232 MB），
bundle 路径 `/var/containers/Bundle/Application/080BB1A5-.../HongKong.app`，
数据容器 `/var/mobile/Containers/Data/Application/A2267FB5-8887-41EE-A5B7-BE6748265D29`。

**状态：排查中，没有可用版本。Round 8 拿到一个可复现的死锁/存活差异，但仍卡在启动图。死因是 `exit(1)`。Round 7 把基线换成"零干预"重测后，真正先下结论的是原因码 4（篡改），它发生在检查表创建之前。**

## 为什么从 hsbcchina 里拆出来

汇丰中国的 1.0.0 做法（把 ZDefend 自杀线程入口改成 `ret`、让威胁列表返回空）对香港版
完全没有作用。香港版没有 ZDefend，也没有 Promon，检测栈完全不同。把两个 App 放在
一个包里名不副实，所以拆成独立项目。

## Round 0 基线（2026-10-27）

不开任何 tweak、用图标点击启动：

| 时刻 | 现象 |
|------|------|
| 0ms | 主进程出现 |
| 约 500ms | 进程号从 11572 变成 11607（旧进程退出，系统重新拉起了一次） |
| 约 900ms | 进程消失 |
| 之后 | 回到桌面，没有崩溃报告，没有 Jetsam 记录 |

挂着探针时同样在 900ms 左右消失。**挂不挂 tweak 表现一致**，说明注入本身不是致死原因，
是 App 自己的判定在启动早期就决定退出。

用户界面上从未看到拦截页——`RASPFramework` 里那些 `acceptJailbroken`、
`JailbrokenStrategy`、`jailbroken_title_advised_ios` 之类的资源一次都没用上，
说明这一版走的是"直接退出"分支，不是"弹页让用户选"。

## 退出机制：已确认为主动 `exit(1)`（Round 1，2026-10-27）

上一轮把结论写成"尚未定位"，是因为看漏了两件事。这一轮用进程外的手段拿到了确定答案。

### 关键事实：是正常的 `exit(1)`，不是被杀也不是崩溃

自写的 `tools/procwatch` 用 `kqueue` 的 `EVFILT_PROC` 观察目标 pid，
注册时必须同时带 **`NOTE_EXITSTATUS`**，否则 `kevent` 返回的 `data` 恒为 0
（只带 `NOTE_EXIT` 时我第一版就踩了这个坑，误以为退出码是 0）。

```
fflags=0x84000000 退出状态 0x100  结束方式：正常退出，退出码 1
```

`0x100` = `WIFEXITED` 且 `WEXITSTATUS == 1`。这解释了几个一直对不上的现象：
没有崩溃报告、没有 Jetsam、没有信号、`atexit` 不触发。App 是**主动调用退出**的，
连 dyld 的析构都没走完（所以 `atexit` 不可靠，不能反推"不是 exit"）。

### 钩子是有效的，之前"零命中"的结论成立

0.0.17 用一个只有 exit 的探针把这件事钉死：

```
exit 前 4 条指令：d503237f a9be4ff4 a9017bfd 910043fd    ← pacibsp; stp; stp; mov
not a trampoline
挂钩后前 4 条指令：58000050 d61f0200 ...                  ← ElleKit 的 ldr x16,#8; br x16
>>> my_exit 被调用，code=9
```

`exit` 入口原本是**真实代码**，`MSHookFunction` 之后确实被改写成跳板，
替换函数也确实被调用。所以 `exit`/`_exit`/`abort`/`kill`/`raise`/`pthread_kill`
在本进程内零命中，是可信的否定结论——App 没有走这些符号。

> 上一轮之所以怀疑钩子失效，是因为观察到的 `58000050 d61f0200` 被当成了
> "hook 前的原始状态"。实际那次读到的是**已经挂上钩子之后**的地址，
> 加上另一次把 `kill` 的 `brk #1` 桩当成"钩子被还原"，两次误判叠在一起。

### 注意 `vm_protect` / `kill` 这类符号是 `brk #1` 桩

`dlsym` 取到的 `vm_protect`、`kill` 头一个字是 `d4200020`（`brk #1`），
它们在这台设备上被 libsystem 替换成了"不可用"桩。ElleKit 对这类地址挂钩会**静默失败**
（不报错，字节也不变）。判断某个钩子到底装没装上，必须回读首字是否变成
`58000050 d61f0200`，不能只看有没有抛错。

### 内联 `svc` 扫描：App 自己的镜像里没有退出类系统调用

在进程内扫了全部 932 个已加载镜像的代码段（`S_ATTR_PURE_INSTRUCTIONS`），
按 4 字节编码找 `svc #0x80` / `svc #0x81`，命中 527 处，分布是：

| 镜像 | 命中数 |
|------|--------|
| `libsystem_kernel.dylib` | 998（`svc` 封装本体，预期之内） |
| `TMXProfiling` / `TMXBehavioSec` / `TMXProfilingConnections` | 24 / 20 / 4（ThreatMetrix 自己的 syscall 封装） |
| `libellekit.dylib` | 4 |
| `PAFaceDetectSDK` | 2 |
| `IOKit` | 2 |

**主二进制 `HongKong` 与 `hsbchkmobilebankingx` 里一处 `svc` 都没有**
（`hsbchkmobilebankingx` 9 MB 整个文件按字节找也只有 1 处，落在非代码区）。

### 尚未解释的矛盾

`exit(1)` 已确认，但所有 libc 退出符号的钩子都没命中。剩下的可能：

1. 退出走的是**早于我们构造函数**的路径——线程在构造函数期间就被改写或劫持了；
2. 走的是 `__DATA,__interpose` 或其他间接绑定，绕开了 `dlsym` 返回的地址；
3. 结论依赖的"零命中"只覆盖了**符号路径**，而 App 用的是自己在 `hsbchkmobilebankingx`
   里的一份 libSystem 调用封装（该框架只链了 libSystem.B / Foundation / CoreFoundation）。

旁证：构造函数返回后约 70ms，探针自己的心跳线程与主线程 tick 会**同时**停止，
而把主线程在构造函数里按 3 秒（0.0.19）时心跳能一直跑到 120 拍。
也就是说，压住我们的东西在主线程上、排在构造函数之后。

### 已排除（本轮新增）

| 手段 | 结果 |
|------|------|
| `kqueue` 外部观察退出状态 | **正常退出，退出码 1** |
| `exit` 钩子有效性自检（0.0.17） | 挂钩成功且替换函数被调用 |
| 全镜像内联 `svc` 扫描（0.0.23） | App 自身镜像零命中 |
| 进程内 Mach 异常端口 | 一条消息都没收到（与"不是异常退出"一致） |
| `signal`/`sigaction`/`task_set_exception_ports` 接管记录 | 只有 `hsbchkmobilebankingx` 的 CPU 计数器探测（`CNTPCT_EL0`/`CNTVCT_EL0`），非检测 |
| 系统崩溃报告 | 19:46–19:49 那三份全是**自己探针**卡住主线程触发的 `0x8BADF00D` 启动看门狗，与 App 无关 |

### 待验证的方向

1. 用 `task_for_pid` 之外的途径（内核层或越狱侧 hook）在**构造函数之前**介入；
2. 在 `hsbchkmobilebankingx` 里定位它自己的进程退出封装——它有 9 MB 代码且完全不 import libSystem 的退出符号。
3. 检查 `UIApplication` 的 `_terminateWithStatus:` 一类私有路径（那是另一种"看起来像 exit(1)"的退出）。



已经排除的路径：

| 手段 | 结果 |
|------|------|
| hook `exit`/`_Exit`/`_exit`/`abort`/`kill`/`pthread_kill`/`raise` | 一次都没命中 |
| hook `syscall(2)`（观察 SYS_exit / SYS_kill） | 一次都没命中 |
| `atexit` 回调 | 没触发，说明不是正常退出流程 |
| 1～31 号信号处理器 | 没收到任何信号 |
| 磁盘文件静态扫描内联 `svc` | 主二进制和 9 个重点框架都没有 exit 类 svc |
| 崩溃报告 / Jetsam 记录 | 都没有 |

**hook 本身是有效的**：探针里对 `getpid` 做了一次自检 hook，调用一次命中一次，
所以"退出函数没被调用"这个结论成立，不是 hook 失效造成的假阴性。

## Round 2（2026-10-27）：用户态拦截这条路走到尽头

这一轮把"退出到底能不能拦住"问到了底。结论是**拦不住**，而且有完整证据链。

### 先纠一个前提：pid 一直是对的

之前"心跳 50ms 就停"是别的 tweak 被禁用状态下的假象。把 pid 与时间轴对齐后：

```
我们注入的进程 pid=19142
procwatch 观察同一个 pid → 退出时刻 uptime ...670，退出码 1
最后一拍心跳             → uptime ...659（相对 386ms）
```

也就是说进程活到约 400ms，退出发生在最后一拍心跳之后 11ms，两者是同一个进程。

### 退出码 1 是真的（做了对照）

| 情形 | procwatch 读数 |
|------|----------------|
| `exit 7` | `0x700` → 退出码 7 |
| `kill -9` | `0x9` → 信号 9 |
| `kill -TERM` | `0xf` → 信号 15 |
| App 退出 | `0x100` → 正常退出，退出码 1 |

`NOTE_EXITSTATUS` 不能省：只带 `NOTE_EXIT` 时读数恒为 0，会被误读成"退出码 0"。

### 不注入我们的 tweak 也一样

移走全部 `HSBCHKBypass*` 后重新启动，仍然读 `0x100`，约 580ms 结束。
所以触发条件是**越狱环境本身**（ElleKit / systemhook 对每个进程都注入），不是本探针。

### 钩子在退出时刻仍然有效

0.0.36 在启动 386ms 时由我们自己的线程调用 `exit(99)`：

```
[386ms] === 主动调用 exit(99) ===
[386ms] !! my_exit 被调用 code=99
procwatch: 退出状态 0x6300 → 退出码 99
```

同一时刻、同一进程，我们的 `exit` 钩子命中并被 procwatch 读到。
所以"App 的 exit(1) 没走 libc `exit`"是可信的否定结论，不是钩子失效。

### 逐条堵，逐条无效

| 手段 | 结果 |
|------|------|
| `exit`/`_exit`/`abort`/`raise`/`pthread_kill`/`task_terminate` 符号入口（MSHookFunction，首字确认 `58000050`） | 零命中 |
| fishhook 重绑所有镜像的 `__got`/`__la_symbol_ptr` | 实测改到 **0 个槽**——App 的镜像里根本没有退出类槽 |
| `syscall` / `__syscall` | 零命中 |
| 把非镜像可执行内存里 `movz x16,#1; svc` 的退出桩改成 `ret`（含持续重扫） | 桩确实改掉，App 照退 |
| Mach 异常端口 | 零消息 |
| `atexit` | 不触发（说明不是 `exit()` 路径） |
| 同步采样全部线程（每 10ms） | 退出前 6ms 三个线程都不在退出路径上 |
| 广泛 hook `stat`/`open`/`fopen`/`_dyld_get_image_name` 隐藏越狱痕迹 | 直接把 App 变成 SIGSEGV（正是 lianjiabypass 记录过的坑），已回退 |

### 静态侧的关键事实

- 主二进制 `HongKong` 的 23394 个导入里**没有** `exit`/`_exit`/`abort`/`kill`/`syscall`/`dlopen`/`dlsym` 任何一个。
- `hsbchkmobilebankingx`（9 MB）只导入 `_abort`，也不导入 `exit`/`_exit`。
- 它的符号名已被剥空（字符串表只有 24 字节），只能从绑定信息取导入名。
- 退出前主线程在 `hsbchkmobilebankingx` 的**哈希循环**里（`mul` + `ror` 反复滚动，
  栈帧约 0xc00 字节），相邻还串联着 `hsbchkmobilebankingx+0x33…`/`+0x65bfa8` 等
  VM 地址——这是一个虚拟机式的内存完整性校验。
- 该框架自带的 libc 兼容层导入 `_kevent`/`_kqueue`/`_pause`/`_tcgetattr`/`_chdir`/`_getcwd`
  之类，看起来像在跑自己的运行时。

### 推论

退出既不走符号、不走 GOT、不走我们能改写的系统调用桩，而 `atexit` 不触发又排除了
`exit()`。剩下的可能只有两类：

1. **退出发生在我们的观测窗口之外**：某个更早的时刻已经决定并排好，最后由 dyld
   或内核路径收尾（例：`UIApplication` 的私有终止路径、或 `_terminateWithStatus:`）。
2. **退出由进程外的实体完成**，内核把状态报成"正常退出 1"。

再往下走，用户态的手段已经用尽。要继续只有两条路：反向分析
`hsbchkmobilebankingx` 那个虚拟机（离线工作，不碰设备），或者在越狱本体层面处理
（roothide 一类只在进程外隐藏注入的做法）。后者与「不动越狱本体」的约束冲突。

## Round 3（2026-10-27）：再排除两个非检测假设

| 假设 | 验证方法 | 结果 |
|------|----------|------|
| 不是检测，而是"iOS 15 太旧"的门槛 | 接管 `-[NSProcessInfo operatingSystemVersion]`、`isOperatingSystemAtLeastVersion:`、`-[UIDevice systemVersion]`，一律报 17.5 | App **一次都没调用**这些接口，照退 |
| 退出由某个后台线程发起 | 启动 336ms 时 `thread_suspend` 挂起除主线程与自身外的全部线程（枚举到 3 个，挂起 1 个） | 照退，退出在主线程上 |

结合 Round 2 的全线程采样（退出前 6ms 无线程处于退出路径）与 0.0.19 里"把主线程
按在构造函数里进程能活 6 秒以上"，可以把范围收到：**决定由主线程做出，
但真正的退出动作不是我们能在用户态插入的任何一种调用**。

# Round 4（2026-10-27）：定位到盾本体，接管它的私有系统调用网关

Round 3 结束时所有用户态拦截手段都试完了，全部无效。那一轮的结论「静态侧主二进制
23394 个导入里没有任何退出原语」后来被证明是**对的**，但当时的推理有缺口：主二进制
确实不导入 `exit`，因为它根本不需要——真正的判定和执行都在 `hsbchkmobilebankingx`
里，而那个框架的导入表我一开始解析错了。

## 1. 盾的身份：Promon SHIELD 的 libshield

`hsbchkmobilebankingx` 的 `__cstring` 里有 290 条构建路径，其中 263 条落在
`/mobile/release/shield/third_party/libressl/`，另有 `shield/libshield-config.pb.cc`。
主二进制还引用了 `_OBJC_CLASS_$_PRMShieldEventManager`。`PRMShield` 是 Promon SHIELD
的类名前缀。

**决定性证据**：这些地址与 llmdoc 里汇丰中国 3.72.15（同一套 Promon 构建）的记录
**逐字节一致**：

| 项 | 地址 | 说明 |
|---|---|---|
| 系统调用网关 | `+0x78befc` | `svc #0x80; ret; brk #1` |
| 网关全局槽 | `+0x8510c8` | 存网关运行时地址，`__common` 里 |
| 网关安装点 | `+0x346c68` | `adrp/add` 算地址后 `str` 进槽 |
| mach trap 封装 | `+0x40c698` | `mov x16,#-0x1f` → 读槽 → `blr x17` |

全镜像共有 **83 个**封装用 `ldr x17,[0x8510c8]; blr x17` 走这个网关。

## 2. 为什么之前所有拦截都零命中

盾的每一次系统调用都经过它自己 `.text` 里的一条 `svc #0x80`，**不经过 libSystem
的任何具名符号**。所以 fishhook 改 GOT、`MSHookFunction` 挂 `exit`/`_exit`、hook
`syscall`、扫内联 `svc`，全部覆盖不到。

## 3. 接管手段：只改一个可写数据槽

网关槽是普通可写数据。把槽里的值换成自己的入口，83 个封装下一次调用就会走进来。
这个办法不需要改任何代码、不需要 `vm_protect`、不碰 `__TEXT`。

第一版探针（0.0.41）立刻成功：盾的每一次系统调用都可见了，调用号在 `x16`，
调用点是返回地址减镜像基址。

## 4. 网关入口必须遵守的两个约束

**（a）不能调用 libc。** 0.0.43 的崩溃报告栈是
`hsbchkmobilebankingx +0x448da0 → gw_entry → gw_log → snprintf → SIGSEGV@0x50`。
盾会在 libc 尚未就绪的线程上调用网关，处理函数里一进 `snprintf`（要读区域设置和
线程局部存储）就踩空。改成「处理函数只把寄存器写进环形缓冲、手写格式化、裸
`svc #0x80` 的 `write` 落地」之后就不再崩。

**（b）x0..x15 全部要保存。** 原网关只有 `svc; ret`，除了 `x0`/`x1` 什么都不改。
中间插一次 `bl` 会按 AAPCS64 把 `x0..x18` 全当调用者保存寄存器用；只备份 `x0..x7`
会让盾里内联在循环中的计数器悄悄变值。

顺带两个测量错误也值得记：`gw_record` 有 6 个参数，第 6 个在 **`x5`** 而不是 `x6`
（按 `x6` 取会把调用点读成垃圾）；mach 消息缓冲区在调用者的栈上，排空线程晚 1ms
再去读，内容早被覆盖，必须处理函数当场拷走。

## 5. 盾看到了什么：逐个头读取每个已加载镜像

解码 `mach_msg` 请求头后：

| 字段 | 值 | 含义 |
|---|---|---|
| `msgh_id` | 4808 | `mach_vm_read_overwrite` |
| `w3` | `0x1_0000_0000` | 目标 task（自己） |
| `w4` | 地址 | 要读的位置 |
| `w5` | 长度 | 常见 `0x20`（32 字节 Mach-O 头），以及后续节表 |

一次冷启动约 **750–1500 次**这样的读取，依次扫过进程里每一个镜像的基址。
注入库（`libellekit.dylib`、`libinjector.dylib`、tweak 自身）**确实在里面**。

## 6. 退出点

```
+0x5d842c:  sub sp,sp,#0x20 ; … ; mov x16,#1 ; mov x0,#1 ; 读网关槽 ; blr ; ret
```

一个无条件 `exit(1)` 的叶子函数，四个守卫函数调用它：
`+0x694e80`、`+0x696774`、`+0x696a08`、`+0x69765c`。崩溃报告里的
`hsbchkmobilebankingx +0x5d8484` 就是它 `blr` 之后那句。

## 7. 试过但**无效**的干预（都是有结论的负面结果）

| 干预 | 结果 |
|---|---|
| 拦退出系统调用（网关处返回） | 进程从 ~100ms 活到 15 秒以上，但停在启动图；截断状态机后主线程再也不恢复 |
| 置空盾的 71 个 `__mod_init_func` | 无效，退出点不变。盾的初始化走 ObjC `+load`，不走 C 构造函数 |
| hook `_dyld_image_count`/`_dyld_get_image_header`/`_dyld_get_image_name` | 无效。**盾根本没导入这些接口**——它一个镜像枚举符号都没有 |
| hook `dlsym` | 无效。装上了但盾一次都没调用 |
| 改写注入库的 `LC_ID_DYLIB` 路径为 `/usr/lib/libSystem.B.dylib` | 无效。改完必须把代码页恢复成 `r-x`，否则 SIGBUS（代码签名） |
| 把退出函数 `+0x5d842c` 首条指令改 `ret` | 部分：偶发能活过 8 秒，但也出现主线程 `pc/lr/sp/fp` 全零的崩溃 |
| 把注入库的 mach 读取重定向到系统 dylib（保持相对偏移） | 生效 9 次，**盾仍在同一处退出** |

重定向那版的细节值得一提：替身不能选盾自己——它是**可执行文件**，第一个 load
command 是 `LC_SEGMENT_64`，而解析器期待 `LC_ID_DYLIB`，会顺着垃圾偏移读崩。
换成 `libobjc.A.dylib` 这类真 dylib 才不崩。

## 8. 当前的核心盲点

**盾是怎么拿到"有哪些镜像、地址是多少"这份准确列表的？**

它没有导入任何 `_dyld_*` 枚举接口，没用 `dlsym`，没发 `vm_region` 类 mach 消息。
但读的地址和每个镜像基址完全吻合（不是扫描地址空间找 magic 那种做法）。
这份列表的来源还没查明，也就没法从"输入侧"切断判定。

## 9. 下一轮应该先做的事

1. **先确认盾有没有在做自身的完整性检查。** 它导入了 `_class_copyMethodList`、
   `_method_getImplementation`、`_method_getName`、`_timingsafe_bcmp`、`_dlsym`——
   这套组合与 ZDefend 的 `apptampering_hooked`（比对自己导入的函数有没有被换过）
   是同一类。0.0.55 只要挂上 `dlsym`，当次运行就在 T+2 秒死了，**很可能就是自曝**。
   所以接下来所有实验都应当只改数据、不碰任何代码，并且一次只上一个变量。
2. 想办法定位那份镜像列表的来源：可以在 `mach_vm_read_overwrite` 的地址序列上做
   文章——看第一次读之前盾刚读了什么、算过什么。
3. 若列表来源无法切断，退回到"让注入库不存在"这个方向：这需要越狱本体层面的
   per-app 黑名单，属于用户已明确排除的禁区，此路在当前约束下不通。

## 10. 回到用户目标

到现在为止，**App 仍然无法正常使用**。可以看到的全部成果是：弄清了盾的身份、
建立了唯一能观察它的手段、找到了退出点、排除了七种干预方式。
第 9 节第 2 条是当前最有希望的下一步。

# Round 5（2026-10-27）：看见判定本身

Round 4 留下的核心问题是"盾从哪拿到镜像列表"。这一轮把它答完了，
并且第一次直接看到了判定是怎么下的、是哪一项在报警。**App 仍然不可用**，
但排查从"猜检测面"变成了"读某一段确定的代码"。

## 1. 镜像列表的来源：dyld 的内存结构，不是任何接口

先把 Round 4 的假设逐个证伪，再给结论。证据来自网关里带真实时刻的完整调用记录。

一次冷启动里，盾在**读第一个镜像之前**只做了三件事：

| 顺序 | 调用 | 说明 |
|---|---|---|
| 1 | `syscall 294` | `shared_region_check_np`，问出共享缓存的实际映射基址 |
| 2 | `syscall 202 mib=[1,2]` | `sysctl`，结果是 `0x0100000000` / `0x4002000000` 一对数值 |
| 3 | `mach_vm_read_overwrite` 读 `缓存基址 + 0`，长度 `0x140` | 拿到共享缓存头原文 |

第 3 步读到的 320 字节开头正是 `dyld_v1  arm64e`，`+0x10` 处 `mappingOffset=0x1c8`、
`mappingCount=6`；紧接着盾按文件 `pread` 了 6 条 `0x20` 字节的映射表项，
完全对得上。**这说明它拿到共享缓存的映射范围，是为了把"住在缓存里的镜像"划出去。**

随后它逐个头读取剩下的镜像。932 个镜像里，共享缓存内 790 个**一个都没读**，
缓存外 142 个读了 141 个。把读到的地址换算成 dyld 的镜像下标，
141 个下标全部落在缓存外，且顺序递增——**它就是按 dyld 的镜像表顺序在走。**

这一步之后到开始读镜像之间**没有任何系统调用**。列表是普通内存读出来的。

## 2. 找到 dyld 的镜像数组，改了没用

在可写内存里按"24 字节记录 {Mach-O 头, 路径指针, 修改时间}"的特征扫，
能找到好几份这样的数组。其中一份长 `0x5a3` 项，末尾三项正是：

```
下标 0x5a0  .../ellekit/libinjector.dylib
下标 0x5a1  .../TweakInject/HSBCHKBypass230226.dylib
下标 0x5a2  .../libellekit.dylib
```

把所有这些数组里的注入条目整条换成一份 App 框架的记录（一次替换 67 条），
盾**照旧**读到那四个注入库的头。所以它读的**不是**这一份。

顺带确认：系统是 dyld4（崩溃栈里全是 `dyld4::`），`_dyld_get_image_header`
在 `libdyld` 里只是个转发桩，真正的实现在 dyld 自己的镜像里——
而 dyld 的进程内本体**不注册成镜像**，所以从 `_dyld_image_name` 里找不到它。

## 3. 判定的形状：一张检查表

沿着退出那一刻的帧指针往上走，退出链路是：

```
exit(+0x5d842c) ← +0x40e840 ← +0x5d908c ← +0x5d8f5c ← +0x5d8890 ← +0x713d40
```

`+0x5d8ed0` 这个函数把判定讲得很清楚：

1. 取一个单例（`+0x5d8490`，指针存在全局 `+0x8509d0`，惰性创建）；
2. **复制**它在 `+0x10` 处的那条向量（`+0x5d91d0`）；
3. 逐项调用每项的虚函数 `vtable+0x10`；
4. 只要有一项返回非零，走到 `+0x5d8f40`，最终以 `w0=5` 调 `+0x40e7e4` 退出。

在退出那一刻就地读出这张表：

```
检查项数=3
  项0  vtable=0x11442cd50  判定=+0x3a2124  结果=0
  项1  vtable=0x11443ea60  判定=+0x6f3d54  结果=1   ← 报警的是这一项
  项2  vtable=0x114425cf8  判定=+0x221514  结果=0
```

三个判定函数都是盾里的虚拟机函数，需要离线反汇编才能读懂各自在查什么。
这是当前唯一确定的检测点。

## 4. 试着让这张表失效

改的是数据，不是代码：把向量改空（终点写成起点），或者把每一项都改指到
"结果恒为 0"的第 0 项。

**结果：退出链路变了。** 从
`+0x713d40 → +0x5d8890 → +0x5d8f5c`（检查表那条）变成
`+0x43e0fc → +0x43ce78 → +0x37d4d4`（另一条，以 `w0=4` 退出）。
两条最终都落到 `+0x40e7e4`，只是原因码不同。

这条经验值得记：**判定不是一个点，是一组点；堵掉一个只是换一条路。**

但没堵住。原因有两个，都是时序：

- 单例是在检查函数**第一次运行时**才惰性创建的，在那之前轮询线程没有对象可改；
- 检查函数遍历的是那条向量的**副本**，副本在循环开始时就已经拷好，事后再改原件够不着。

尝试提前把单例建出来（直接调 `+0x5d8490`）会立刻 SIGSEGV——盾的初始化没完成时
不接受外部调用。这条路也划掉。

## 5. 排除掉的一个假设

一直怀疑它把主二进制的 load command 从磁盘读出来跟内存比。实测：

- 它确实 `open` 主二进制后按 `pread` 逐条读 load command（偏移 `0x0` 到 `0x5670`，
  先读 8 字节 `cmdsize` 再读整条命令，一共 449 次 `pread`）；
- 但把内存里同一段 24576 字节 dump 出来跟磁盘原文比对，**逐字节完全相同**。

所以这条比对是过的，不是它报警的原因。（顺带说明：这也意味着主二进制没有被人动过。）

## 6. 这一轮新增的工具

- **每条记录带真实时刻**：网关里用 `mrs x0, cntpct_el0` 取硬件计数，
  排空线程用两次采样标定每毫秒的计数再换算。寄存器读不调库，符合网关的约束。
- **帧指针回溯**：网关入口把 `x29` 存进记录，排空时沿帧链走，只保留落在
  盾镜像范围内的返回地址。退出链路和镜像读取的发起位置都是这么拿到的。
- **判定现场读检查表**：在 `emergency_line`（退出系统调用前的那一句）里
  直接读单例和容器，并逐个调用检查项，拿到 `结果`。

## 7. 未解与下一步

1. **`+0x6f3d54` 到底在查什么。** 它返回 1，是明确报警的那一项。
   它是虚拟机函数，静态读需要先摸清那套分发的形状；更快的办法是
   在它运行的那几毫秒里把它的输入（它读过的内存、它的参数对象）记下来。
2. **另一条退出路径（`+0x37d4d4`，原因码 4）的触发条件。**
   它在 92ms 到 101ms 之间发生，这段时间里**没有任何系统调用**，
   说明是纯内存判定。
3. 这两条路都不是最终答案——把检查项都改成"通过"只会在别处再冒出来。
   真正要解决的是让盾的**输入**不含注入痕迹，也就是第 2 节里没找到的那份列表。

## 8. 补充实验（同一天，接在 Round 5 之后）

| 干预 | 结果 |
|---|---|
| 把检查对象 `+0x08` 那个全 1 位掩码清零 | 无效，两条退出路径照旧 |
| 提前调 `+0x5d8490` 把单例建出来，再清空 | **SIGSEGV**——盾的初始化完成之前不接受外部调用 |
| 把报警项 `+0x6f3d54` 的头两条指令改成 `mov w0,#0; ret` | **退出点又换了**：从检查表那条变成 `+0x43a190`（初始化路径内），且两次运行中有一次 SIGSEGV |

最后一条是这一轮最有信息量的负面结果：**判定不止一处**，把检查表那一项改掉之后，
初始化路径里还有另外的判定点（`+0x43e0fc → +0x43c978 → +0x43a190`）。
单点改代码只会把退出换到另一条路上，还可能把自己打崩，所以已经全部关闭，
探针恢复到只观察（0.0.100）。

改代码那次用的页权限处理值得记：`mach_vm_protect` 改成可写、写完立刻恢复
`READ|EXECUTE`，再 `sys_icache_invalidate`。直接用 `MSHookFunction` 会 SIGBUS。

## 9. 拦截的最后一道墙：注入本身无法对单个 App 关闭

这一节是 Round 5 之后继续尝试的结果，结论是**当前约束下这条路走到头了**。

| 尝试 | 结果 |
|---|---|
| 把上报函数 `+0x40e7e4` 改成直接返回（一次覆盖所有退出路径） | 补丁装上（`ok=1`），进程 **SIGBUS**——盾的自检抓到了代码改动 |
| 就地改注入库的 `LC_ID_DYLIB` 路径（字符串在代码页里，改它等于同时改 dyld 列表与 LC_ID_DYLIB，两边永远一致） | `systemhook` 的路径太短写不下；能写的那些一写就 SIGBUS，同样卡在代码签名上 |
| 清空检查表 + 重定向注入库的镜像读取，持续高频轮询 | 重定向生效 669～1327 次，检查表在 93ms 清空，但盾在 ~98ms 仍走检查表那条退出——向量被重新填回去了，我们始终晚一步 |

**根本原因**：Round 2 就测过——把本项目的 tweak 全部移走，App **仍然** `exit(1)`。
也就是说触发条件是越狱环境本身的注入（`systemhook.dylib` / `libinjector.dylib` /
`libellekit.dylib`），不是我们的探针。而设备上的 ElleKit 没有按 App 排除的配置：
`libinjector.dylib` 里只有 `/var/jb/usr/lib/TweakInject/` 和 `.plist`，没有任何
blacklist / exclude / bundleid 一类的开关，它是无条件注入的。

于是形成一个闭环：**App 只要被注入就自杀，而注入无法对单个 App 关闭**——
除非改越狱本体，那是用户明确排除的禁区。

当前可选的只有两条，都需要用户决定：

1. **在越狱侧做 per-app 排除**（改 `libinjector` 或换支持排除列表的注入器）。
   这是唯一能让盾看到"干净进程"的路径，但违反"不动越狱本体"的约束。
2. **继续在进程内打**：需要先解决"检查表被重新填充"的时序，并且还要同时解决
   第二条退出路径（原因码 4）。工程量大，且改代码已被证明会触发自检。

## 10. Round 6（2026-10-28）：继续在进程内打，又撞上完整性自检

用户选择"继续在进程内打"。这一轮把能想到的点都试了，结果如下。

### 10.1 改代码一律触发自检

| 做法 | 结果 |
|---|---|
| 把上报函数 `+0x40e7e4` 改成 `mov w0,#0; ret`（一次覆盖所有退出路径） | 补丁装上（`ok=1`），**SIGBUS** |
| 就地改注入库的 `LC_ID_DYLIB` 路径（同时改掉 dyld 列表与 LC_ID_DYLIB，两边永远一致） | `systemhook` 路径太短写不下；能写的那些一写就 **SIGBUS** |

两次都是同一个原因：写的是代码页，代码签名不让过；而 `mach_vm_protect` 的
`VM_PROT_COPY` 之后再恢复 `R|X` 也救不回来。

### 10.2 报警项是纯内存判定，而且没有可改的标量

在退出那一刻调用报警项 `+0x6f3d54`：返回 1，**整个调用期间没有任何系统调用**
（网关里一条记录都没有）。说明它的判据是早就存好的内存状态。

于是拿它当预言机：逐个把检查对象 `+0xb0` 字节里的字段清零，看哪个一清就把 1 变成 0。

- 连指针字段一起试 → **SIGABRT**（解引用了清零的指针）
- 只试不像指针的标量 → 跑完了，**一个都没能翻转结果**

结论：判据藏在指针指向的子对象或全局状态里，不在对象表面。

### 10.3 堵掉检查表只会换来"篡改"判定

用忙等（不休眠）持续把检查表的终点写成起点，抢"填充"和"复制"之间的空档：

- 成功：`改指时刻 90ms`，盾确实不再走检查表那条退出路径；
- 但退出改走 `+0x43e0fc → +0x43ce78 → +0x37d4d4`，**原因码 4**。

对比基线（不清空时走检查表、原因码 5）可以确定：**原因码 4 是"被改过"的报告**。
也就是说盾有一套完整性自检，任何对它的改动都会被记账。忙等本身还引入了竞态，
三次运行里有两次是我们的改动造成的 SIGSEGV / SIGABRT。

### 10.4 找到了 dyld 的镜像数组，但盾不用它

`_dyld_get_image_header` 在 `libdyld` 里的桩是这么写的：

```
adrp x8, #0x202acd000
ldr  x0, [x8, #0xcd0]      ← dyld 的 AllImages 对象
ldr  x16, [x0]             ← 虚表
ldr  x2, [x16, #0x20]!     ← 方法
braa x2, x17
```

顺着这个全局拿到的对象（本机 `0x113b14060`）里：

| 偏移 | 含义 |
|---|---|
| `+0x28` | 镜像数组（`Loader*` 的数组） |
| `+0x30` | 条目数（932） |
| `+0x38` | 容量（1024） |

每项是 `Loader*`，其 `+0x8` 就是这个镜像的 Mach-O 头。把注入库的条目
和末尾对调、条目数减一（纯数据，不碰代码页），摘掉 3 条之后**盾照旧退出**。

**所以盾用的不是 dyld 这份数组。** 这条否证很重要：它排除了最自然的那个假设。

### 10.5 结论

在"不改越狱本体"的前提下，进程内这条路本轮没有走通，而且失败的原因高度一致：

1. 改代码 → 代码签名 / 完整性自检（SIGBUS、原因码 4）
2. 改盾的数据结构 → 单例惰性创建 + 向量会被重建，时间窗抢不到；抢到了也会被记账
3. 改没有注入库的假设源（dyld 数组）→ 那不是它的输入

剩下真正没被否证的只有一件事：**盾到底从哪拿到那 141 个缓存外镜像的地址。**
它读的地址精确对应镜像基址，却既不用 `_dyld_*`、也不用 dyld 的 AllImages 数组。
下一步应该从 `+0x6f3d54` 的内部（它读的那个子对象）往回找，而不是继续猜。


## Round 7（2026-10-28）：先把观测修好，再问"到底谁先开火"

Round 5/6 的结论是"判定是一张检查表，唯独 item1 返回 1，堵它只会换一条退出路"。
本轮从那条线索接着走，结果发现**那个结论建立在坏掉的观测上**：清掉全部干预之后，
App 的死法根本不是检查表，而是另一路，而且更早。

### 7.1 先修观测（三个污染源）

这一轮一开始花了很大力气怀疑"结论不稳定"，最后查出来全是自己的问题：

- **时间戳恒为同一个数。** `rec_ms()` 以标定时刻为锚点，而 `calibrate_pct()` 在构造
  函数末尾调用、里面还 `usleep(50ms)`。结果每段日志里所有记录都显示同一个毫秒数
  （59ms、56ms、55ms…），时序信息等于没有。改成以构造函数开始时的 `g_ts0` 为锚点，
  并让所有直接写的日志行也带时刻、整行一次 `write` 写完。
- **每毫秒新建一个心跳线程。** `poller()` 的循环体里有 `pthread_create(heartbeat)`，
  循环 30000 轮。一次启动里会有成百上千个线程同时改写检查项、同时写日志，
  日志行被切成碎片（出现过 `[1003ms] [1003ms] 线程快照` 这种断行）。
  改成构造函数开头只建一次。
- **上一轮的破坏性实验还留在代码里。** `gw_record` 里对注入库的读取重定向，
  注释写的是"改指到一个真正的系统 dylib"，实际代码是
  `*srcp = 0x400000000000ULL`——让盾的读取失败。这个"让读取失败"的变量一直在场，
  和后来叠上去的检查项改写混在一起，退出链路自然对不上任何单一原因。

**教训：一轮实验结束要把开关关掉并写进记录；否则下一轮所有结果都被它污染，
而表现是"改了但没用"，看起来像手段不够好。**

### 7.2 零干预基线

`0.0.136`：接管网关只做记录，不改任何数据（`DO_REDIRECT 0`、`DO_FAKE 0`）。

8 次冷启动，**全部在 51-56ms 以原因码 4 退出**，调用链固定：

```
exit(1) ← +0x40e7e4(原因码 4) ← +0x37d4d4 ← +0x43ce78 ← +0x43e0fc
```

而"检查表"那条链（`+0x713d40 → +0x5d8890 → +0x5d8f5c → +0x5d908c`，原因码 5）
在这 8 次里**一次都没出现**，`检查表单例出现` 这条日志也是 0 次。

也就是说：**原因码 4 在检查表建立之前就下结论了。** Round 5 追的 item1 是真实存在的
第二道判定，但它不是最先开火的那一道。

### 7.3 原因码 4 之前发生了什么

把 40-64ms 每隔 3ms 拍一次全线程快照（含 `x0..x8`），主线程的走向很清楚：

- **40-43ms**：逐张读镜像头部。每个地址读 0x20 字节，再读 `base+0x20`、长度等于
  `sizeofcmds` 的 load commands。一次运行里读到 148 个不同地址，**4 个注入库里有 3 个
  被读到了**（`systemhook.dylib`、`HSBCHKBypass*.dylib`、`libellekit.dylib`）。
- **44-60ms**：进入 `+0x65bfa8`。这段是 **xxHash64**（`0xC2B2AE3D27D4EB4F` /
  `0x9E3779B185EBCA87` 两个素数，4 路并行累加），一次哈希一段镜像。
  快照里 `x1` 指向 `GlobalCore`、`PlatformAnalyticsIntegration`、`MobileContentStore`、
  `LegacyVASCODSK` 以及盾自己这些镜像的内部。
- 调用点是 `+0x43cccc`，返回后立刻 `cmp x21, x20`（期望值 vs 算出来的哈希），
  再回 CFF 派发器。这一步直接发生在 `mov w0,#4` 之前。

**观察（不是推论）：盾在判定前对镜像内容做了整体哈希并比对。**

### 7.4 两次否证

- **把注入库的头部读取改指到替身库**（`RASPFramework`，结构完整、签名有效的 dylib 头，
  相对偏移不变）。结果：仍然在 51-60ms 以原因码 4 退出。
- **把落在注入库上的读取改成一整页零**，让盾读到的头没有 Mach-O magic、认不出是镜像。
  结果：仍然以原因码 4 退出（3 次里 2 次 57-59ms 退出，1 次走到 3051ms 的另一条链）。

所以**从读取侧让注入库"消失"不改变结论**。要么那份镜像清单不是从这些读取建立的，
要么原因码 4 根本不由注入库触发。

### 7.5 控制实验：是不是我们自己的接管导致判定

`0.0.140`：`try_takeover()` 直接返回，网关槽不动，tweak 只加载不做事。

4 次冷启动，进程外观察（`procwatch`）全部正常退出、退出码 1，时间与接管时一致。

**推论：判定与我们的拦截无关。** 这条排除掉了一个一直悬着的可能——"是不是我们接管
网关槽这件事本身被盾发现了"。

### 7.6 本轮排除与保留

已排除：

1. "检查表（item1）是最先开火的判定" —— 零干预下它根本没被创建。
2. "从读取侧隐藏注入库能改变原因码 4" —— 替身库、全零页两种做法都无效。
3. "我们自己的网关接管触发了判定" —— 不接管照样退出。
4. 观测层面的三个污染源（时间戳、多心跳线程、残留的破坏性实验）已修复。

仍然未知：

- 原因码 4 的**具体触发条件**。xxHash 那一步比对了什么、期望值从哪来，还没查到。
  可能是镜像内容清单，也可能是共享缓存（越狱会改写它），两者都没有证据分辨。
- 已有观测显示：干预开启时，约 1/3 的运行不死于原因码 4，而是所有线程停住、
  网关计数冻结，3 秒后由 `+0x5d8758`（`[单例+0xa]=1` 后转调）退出。
  那是一次**死锁**，不是"跑起来了"：快照显示 4 个线程两次采样完全没动，
  `累计=3357` 从 1 秒到 3 秒一动没动。

### 7.7 哈希的对象与"内存是否被改"（同一轮继续）

用 0.2ms 采样把哈希阶段跨过的指针抓下来，再用运行时的镜像基址表反查：
`x1` 落在的全是 **hsbchkmobilebankingx 自己的代码页**（`+0x18000`、`+0xd4000`、
`+0x14c000`、`+0x2a8000`、`+0x318000`…）。也就是说那一步是**对自己的自检**，
不是对别人的检查。

于是直接比了一次：把盾的 `__TEXT`（0x80c000 字节）与磁盘文件逐页比对，
**不同的页数 = 0**。再把比对扩展到所有能打开的镜像：

- App 自己的框架（`GlobalCore`、`MobileContentStore`、`LegacyVASCODSK`…）**全部一致**。
- 唯一不同的是主二进制 `HongKong` 的 `+0x8000` —— 但它的 `__TEXT` 是 FairPlay 加密的
  （Round 4 已测出 `cryptid=1`），内存里是解密后的字节，这个差异本来就应该存在。

**所以原因码 4 不是"发现内存里的代码被改过"。** 这条也排掉了。

顺带把盾的导入表看全了：只从 libSystem 导入，没有任何 Security.framework 符号，
所以它不能直接调 `SecStaticCode` 一类接口做签名校验；能用的是 `_dlsym`、`_mprotect`、
`_uname`、`_getenv`、`_readlink`、`_realpath`、`_opendir`、`_timingsafe_bcmp`。

### 7.8 被漏掉的一整类观测：直接内存读

网关只能记录**经过它自己 `svc` 网关**的调用。盾从共享缓存头、dyld 结构、
以及它自己构造的清单里读数全部是普通内存访问，这些完全看不见。
Round 5 说"这段窗口里零系统调用，清单来自普通内存读"，就是这件事的直接后果——
**我们已经知道清单是读内存得来的，却无法看见读了哪一段。**

这也解释了为什么"改注入库头部的读取"这类手段全部无效：能改的只有走网关的读取，
而清单很可能是直接读内存拿到的（路径字符串、条目数都在里面）。

### 7.9 下一步的单一假设

下一步只验证一件事：**原因码 4 是不是按"镜像集合里有不该有的东西"下的结论。**

做法：在盾构建清单之后、判定之前（约 45-50ms），把它枚举到的镜像基址集合
与我们自己 `_dyld_*` 得到的集合各存一份并比对，看差在哪几张；同时用
`vm_region` 枚举出所有可执行映射，检查盾是否有不经过网关的清单来源。
如果差异正好是注入库，下一步就是断掉那份清单；如果没有差异，
原因码 4 就得往进程环境（`uname`、`getenv`）或端口表方向找。


## Round 8（2026-10-28）：把观测补到判定前，逐个否证候选触发条件

Round 7 已经把基线换成"零干预"，确认先开火的是原因码 4。这一轮继续往下挖，
主要成果是**把观测推到判定前那十几毫秒**，并逐个否证了几个候选触发条件。

### 8.1 观测本身在扰动被测对象（重要）

同一份代码，只改"要不要做密集线程快照"（36-62ms 每 0.2ms 一次 `task_threads`，
26ms 内约 120 次），判定结果整个换掉：

| 配置 | 结果 |
|---|---|
| 安静（不做密集快照） | 5/6 次原因码 4，1/6 次原因码 5 |
| 密集快照 | 4/4 次原因码 5 |

**结论：`task_threads` 这类全局暂停式采样不能当作"只读观测"。** 之前"两路判定谁先跑完"
看到的不稳定，有一部分是探针自己造成的。之后的判定类实验必须在安静模式下做。

### 8.2 补上判定前的日志（本次最有用的改动）

环形缓冲在判定前那几十毫秒里落后几百到上千条，而进程紧接着就退出，**最要紧的那一段
从来没写出去过**。所有日志都停在 41-49ms，而退出发生在 53-60ms。

在 `gw_record` 的退出分支里同步 `flush_ring()`（把缓冲剩余记录全部写出）之后，
才第一次看到判定的完整上下文。

### 8.3 逐个否证

- **往 dyld 的 AllImages 数组插哨兵**：追加一条并把计数加一 → 进程立刻 **SIGABRT**；
  改成原地覆盖末条、计数不变（连原 Loader 前 0x40 字节整块抄过来）→ **SIGSEGV**。
  把哨兵挪到构造函数末尾、我们自己的 `_dyld_*` 调用全部之后，照样崩。
  **dyld 自己在校验那份数组，这条路不能用来做判定实验。**
- **改写注入库在 dyld 里登记的路径**（换成 `/usr/lib/libobjc.A.dylib` 一类，4 条全部改写成功）
  → 仍然原因码 5。**路径不是它的判断依据。**
- **把落在注入库上的头部读取改指到 App 自己的框架**（结构完整、签名有效的 dylib 头，
  相对偏移不变，命中 90-153 次）→ 仍然退出，无改善。
- **全局 `+0x866fc8`**：`+0x43ce74` 之后紧跟 `ldr` 它并 `cmp #0`，所以一度以为"非零即原因码 4"。
  实测这个位置**整轮恒为 0**，紧接着的 `0x10043c15c` 也只是又一个派发块，不是"零就放行"。
- **延迟 dlopen**：想在枚举之后加载新库、看盾会不会读到，以此判断它的清单是不是靠
  dyld 回调累积的。试了 6 个候选（GLKit、Speech、GameCenterFoundation、OnBoardingKit、
  CoreAudio、MediaRemote），`dlopen` 都返回成功但**镜像数没有增加**——这些库在这台机器上
  要么已在缓存里被直接映射、要么根本没有新镜像，这个实验做不成。

### 8.4 一条还没查的线索

盾在启动时 `open` 了三份 **App 包内**的资源，而设备上它们的状态是：

| 文件 | 设备上 |
|---|---|
| `HongKong.app/bi.txt` | 存在，37028 字节 |
| `HongKong.app/config-encrypt.txt` | 存在，15616 字节 |
| `HongKong.app/jigsaw.txt` | **不存在**（`find` 也找不到） |

`jigsaw.txt` 打不开这件事在每次启动里都发生。它是不是"文件缺失 → 判定为篡改"，
还没有证据分辨——但这是目前唯一还没被否证的、指向"盾期望的东西不见了"的线索。

### 8.5 存活时间变长，但仍不可用

改动之后出现过进程活 4-9 秒的情况（之前是 1 秒内），连续三次测量是 5s / 2s / 1s，
**不稳定**；3 秒时截图停在启动图（汇丰 logo），7 秒时进程已消失。

日志里还看到一种现象：记录到 `exit(1)` 被调用，但进程继续跑了三秒多；
同一个 pid 的心跳从 50ms 一直写到 3767ms。这段还没解释，不能当成"拦截成功"。


### 8.6 环境因素清点（按"继续枚举环境因素"的要求）

把一次完整运行里盾发起的调用按编号汇总，全部列在下面。这份表的价值在于：
**没出现在表里的东西，就是它没查的**，不用再猜。

### 8.7 本轮结束时的判断

在"不改越狱本体"的约束下，进程内这条路仍然没有走通。已经排除的清单（累计）：

1. 改代码 / 改虚表 / 改检查表 → 原因码 4 或 SIGBUS
2. 从读取侧隐藏注入库（替身库、全零页、改路径）→ 无效
3. 改 dyld 的 AllImages 数组 → dyld 自己崩
4. 我们自己的网关接管 → 不是原因（不接管照样退出）
5. 内存中的代码与磁盘不一致 → 已逐页比对，只有 FairPlay 加密的主二进制"不同"
6. 文件系统痕迹 → 它只访问共享缓存和 App 自己的资源文件
7. 共享缓存正文完整性 → 只 pread 头部，没有整文件哈希

**剩下最可能的、还没被否证的一条**：它把共享缓存整个 `mmap` 进进程，然后用普通内存访问
去比对镜像内容。这条路我们看不见、也改不了——除非在 `mmap` 这一步做文章（把这次映射
换成一个我们能控制的内容源），而这已经不是"改数据"的范畴了。

## Round 9 续：那个矛盾现象查清了，而且它推翻了之前的一个读法

### 现象

日志里记录到 `exit(1)`（55ms 左右），但用 `ps` 逐秒探测时进程还能在 5-8 秒后才消失，
于是看起来像"退出被拦住了、进程活得更久了"。

### 查法

一次干净的冷启动，边启动边按 0.5 秒采样 pid：

```
1: [20353]  2: [20353]  3: [20353]  4: [20353]
5: [20384]  6: [20384]  7: []  8: [] ...
```

再把这一轮的日志取下来数启动标记：**两条 `===== 启动`，两个不同 pid**。

### 结论

**系统在 App 死掉之后会把它重新拉起一次，而两次的日志写在同一个文件里。**
之前把所有心跳按时间排起来看，等于把"第一个进程死前"和"第二个进程活着"接成了一段，
于是得出"活了 5-8 秒"这个假结论。

**退出其实一直是生效的。** `exit(1)` 发出之后进程就没了，没有任何一次实验真的延长过
单个进程的寿命。

### 修正后的基线（0.0.166，退出记录带 pid）

```
冷启动 1: 首个 pid 22001 只活到第 1s（期间 pid 又出现过 1 次，那是系统重新拉起的另一个进程）
冷启动 2: 首个 pid 22110 只活到第 0s（期间 pid 又出现过 1 次，那是系统重新拉起的另一个进程）
```

`verify.sh` 已经改成按 pid 统计，pid 一变就单独标出来，不会再把这个假象算成存活。

### 因此要撤回的判断

Round 8 里写的「存活时间变长（4-9s）但不稳定」**是错的**，不应作为任何结论的依据。
当时截图停在启动图，那是第二个进程的启动图。

**教训：进程类目标的存活测量必须绑定 pid。**"进程还在不在"这种问题，
用 `ps` 按名字匹配会在"目标被系统拉起"时给出错误答案，而错误的方向恰好是乐观的
（看起来活得更久），最容易被当成进展。


### 9.5 用修好的测量重做"拦 exit"

既然退出一直是生效的，之前"拦住 exit 就能活更久"就得重测。做法是在网关里
**不把第 1 号系统调用发出去**，直接让调用返回 0（只改控制流，不碰代码和数据）。

结果（绑定 pid 的测量）：

```
冷启动 1: 首个 pid 22788 存活 0s（pid 没变过）
冷启动 2: 首个 pid 22895 只活到第 3s（期间 pid 又出现过 1 次）
```

日志显示 pid 22895 有**两次** exit 记录（54ms 走原因码 4、654ms 走原因码 5），
两次都被拦住了，然后一直活到 2970ms，**没有第三次 exit 记录**就没了。

用进程外的 `procwatch` 看首个 pid 的真实死法：

```
退出状态 0xb  结束方式：被信号终止，信号 11 (SIGSEGV)
```

**所以拦住 exit 之后，进程不是"继续启动"，而是 0.7-3 秒后以 SIGSEGV 收场。**

exit 函数在网关调用之后还有一步：`+0x5d8488  mov w0,#1` / `+0x5d848c  bl +0x774770`，
而 `+0x774770` 是一条 `adrp x16,0x10084c000; ldr x16,[x16,#0x98]; br x16` 的跳板，
指向盾自己那张间接函数表里的下一站。跳过网关那一站，调用方照旧往下走，
拿到的是它并不期待的状态，于是崩在后面的路径上。

这和 Round 4 的结论一致，只是这次有了确切证据：
**在系统调用中间截断，调用方永远回不来；要改变控制流，必须在函数边界上做。**


## Round 10：给"已验证的否证"和"没验证的否证"划清界线

### 10.1 先补上自己漏的那一步

Round 9 里"让共享缓存整体映射失败"那次实验，我只看了 `已重定向=0` 就当成结论——
**根本没有验证干预是否生效**。按方法论里自己写的那条（干预必须报"我生效了 N 次"），
这次补上计数后重做：

```
已拦下整份缓存映射 长度=0x5acf4000
  累计拦下=0x1
```

每次启动拦下 1 次、长度 1.42 GB，**判定完全不变**。
所以"共享缓存内容比对"这条现在是**真否证**，不再是悬着的一个猜测。

### 10.2 共享缓存头：内存与磁盘逐字节相同

盾读过缓存头的 0x140 字节（`pread len=0x140 off=0`）。拿进程内那份 dump
（`探针 地址=0x1a8ef4000`，320 字节）和设备上 `dyld_shared_cache_arm64e` 的前 320 字节比对：

```
不同的字节数 0
```

**"内存里的缓存头被越狱改过"这条也排除了。**

### 10.3 关于 exit 生效不生效的两个读数互相矛盾

- 0.0.168 那次：pid 23675 在 60ms、65ms 各记录一次 exit，但它的心跳一直写到 2260ms。
- 0.0.169 这次：心跳停在 350ms，exit 记录在 414ms，进程随后消失。

两次读数互相矛盾，说明**是我的观测手段不稳定**，不是 App 真的活得更久。
原因很可能是退出瞬间那次同步冲刷环形缓冲会把大量积压记录一次性写出去，
时间戳与实际写入顺序对不上。

**结论：以"exit 之后还有没有心跳"来判断退出是否生效，这个方法不可靠。**
要判断死因应该用进程外的 `procwatch`（它给的是内核的 wait 状态），而不是进程内日志。

### 10.4 本轮新增的可复用教训

- **干预不报计数，结论一律不算数。** 一个"改了但没用"和一个"根本没改上"，
  在日志上长得一模一样，而后者会让你错误地排除一整条正确的路。
- **进程内的日志顺序不等于事件的时序。** 排空线程、退出时的同步冲刷、
  多进程写同一个文件，三者叠加之后，靠日志推断"谁先谁后"非常容易出错。


## Round 11（2026-10-28）：换到函数边界上改——界面第一次真正出现

### 11.1 找到真正的收尾跳转，而不是拦系统调用

盾的退出函数（`+0x5d842c`）不以退出系统调用收尾，它发完 `exit` 之后还有一步：

```
+0x5d8488  mov w0, #1
+0x5d848c  bl  0x774770        → adrp x16,0x84c000; ldr x16,[x16,#0x98]; br x16
```

而且编译器把整个函数按"不返回"排布：`0x5d8490` 紧接着就是下一个函数的序言。
所以之前所有"在系统调用处拦一下"的做法注定失败——调用方带着错误状态往上走，
最后崩在后面，与 Round 10 的结论一致。

新做法是把 `[0x84c098]` 这个槽换成一段替身：取回调用者的 `x29/x30`、
把 `sp` 抬回去、直接 `ret`，等于这个退出函数正常返回给了调用方。

### 11.2 中途踩的三个坑，每个都会让结论失真

**坑一：那个槽有 30 处代码在用。**
`bl 0x774770` 的调用点有 30 个，退出函数只是最后一个。第一版替身对所有调用者
一律按退出函数的栈帧弹栈，结果是"活几秒就 SIGSEGV"。改成按调用者分流：
只有从 `0x5d848c` 过来的才走正常返回，其余原样跳回盾自己原本要去的目标。

**坑二：跳过标志是"一次性消耗"的。**
原来的实现是 `gw_record` 置位、网关读一次就清零。盾会从两条线程几乎同时调用 `exit`，
于是 A 线程置位、B 线程（恰好是一个无关的 `open`）把名额领走，
那个 `open` 返回了 0（stdin），而 A 线程的 `exit` 反而真发了出去。
证据：`跳过返回=0x…3b8a68` 正是那次 `open` 的返回地址。
现在改成只比系统调用编号，不消耗任何状态。

**坑三：网关一直在破坏盾的寄存器。**
还原 `x0..x15` 之后又用 `adrp` 覆盖了 `x9/x10/x11`，而 `bl _gw_after` 之后
`x7..x15` 根本没恢复。盾专门把这些寄存器存起来（83 个封装都这么做）就是怕被改，
我们每次系统调用都在改。已改成只把 `x0/x1` 落盘、其余全部按原值还原。

另外 `g_skip_svc` 原来声明成 `int`，汇编却用 64 位 `ldr/str` 访问它；
调整代码布局后它落到 `0x1100c`，链接期才发现"8 字节访问未对齐"。

### 11.3 结果

修完上面三处，冷启动不再 SIGSEGV（退出方式变成脚本自己的 `SIGKILL`），
**界面第一次真正出现**：汇丰 HK 的标志启动图（截图见 `/var/tmp/hk/keep/splash-0.0.170.jpg`）。

日志证据（同一次启动）：

```
[667ms] 替身被执行了
[5351ms] 心跳 pid=38077 ... 下一站命中=2
```

替身被调用了两次——说明盾在大约 0.6 秒和 5 秒各走了一次退出流程，两次都被正常返回。

### 11.4 还没解决的

App 停在启动图，没有进到登录界面；存活时间在 0 到 5 秒之间波动，不稳定。
下一步要查的是：启动图之后主线程卡在哪个库。线程快照已经能按镜像表解析地址了。

### 11.5 顺手修掉的工具问题

- `verify.sh` 取 dylib 的规则改了：debug 和 release 两份会同时存在，而 `make`
  只更新 debug、`make package` 只更新 release。之前它固定取 debug，
  结果 0.0.170 第一轮部署到几小时前的旧构建，日志抬头还写着上一版，白跑一轮。
  现在取较新的那份，并把大小和修改时间打出来。
- 网关记录改成按 1/200 采样（`exit` 与 mach trap 照常记）。盾每秒过 6-7 万次系统调用，
  全记下来日志几秒就 25MB，探针自己成了负载，把存活时间也搅乱了。


## Round 12（2026-10-28）：拦住退出之后，App 为什么还是起不来

### 12.1 一个必须先纠正的事实

`DO_BLKEXIT` 这个开关从 0.0.169 起只是**声明**、代码里从来没引用过——也就是说
此前每一轮所谓的"零干预基线"其实都带着"拦下 exit"这个干预。结论本身不错，
但"零干预"这个说法要按"拦了 exit"重读。

### 12.2 关键结论：拦或停住退出流程，App 都不会起来

两种处理方式都试过，结果一致：

| 处理方式 | 计数 | 结果 |
|---|---|---|
| 让那条线程原地停住（`wfe` 死循环） | 1 次 | 进程活 14 秒，屏幕全黑，全部线程停在 `libsystem_kernel` 等消息 |
| 按栈帧正常返回给调用方 | 1-2 次 | 进程活 12 秒，同样黑屏 |

与此同时，盾的网关计数在几百次之后就**不再增长**——盾把自己的检查线程撤了，
而 App 那边在等一个永远不会来的结果。

**所以问题不是"进程被杀"，而是"盾的检查没有正常完成"。**
App 的启动被盾的检查结果卡着：检查不通过就退出（原来的行为），
检查被我们打断就永远等下去。要让 App 可用，只能让这项检查**真正通过**。

这条推翻了 Round 4-11 的基本假设。之前所有"拦住退出"的努力，
即使成功也只会把一个 50 毫秒的崩溃换成一个无限期的黑屏。

### 12.3 顺手纠正的两处旧笔记

- **`jigsaw` 不是文件。** 盾里有 `no.promon.shield.ios.model.JigsawInformation`
  和 `JigsawDataBlock` 两个类，Jigsaw 是 Promon 自己的完整性清单模型。
  早前把"`jigsaw.txt` 打不开"当成缺文件，是读错了。
- **盾确实导入了 `getenv` 和 `uname`。** 早前笔记写的"没有 getenv、没有 uname"
  是错的。不过实测运行期只看到 Foundation 自己问了一次
  `CFFIXED_USER_HOME`，盾并没有走 libc 这条路。

### 12.4 检查表的时间窗只有 4 毫秒

诊断输出显示：67ms 时检查表单例已经存在，但它的向量 `bg`/`en` 还是 0；
71ms 就已经走完退出流程。也就是说"填向量 → 复制 → 逐项判定 → 退出"
全部发生在 4 毫秒之内，而心跳线程在这个窗口里只抢到了"向量还是空的"那一瞬间。

想在不动代码的前提下改判定，必须在这个窗口里抢到。已经写好的
`patch_verdict_vtables()` 就是为此准备的：保留真实检查项对象（堆上分配的，
盾的自检哈希覆盖不到），只把对象自己的虚表指针指向一份拷贝，
把拷贝里 `+0x10` 那一格换成恒返回 0 的桩。代码就绪，但这几轮都没抢到窗口。

### 12.5 这一轮确认可用的东西（没白跑）

- **网关修好了三处**：跳过标志不再被无关系统调用抢走、不再破坏 `x9..x15`、
  `g_skip_svc` 改成对齐的 64 位。冷启动不再无故 SIGSEGV。
- **替身的两条分支分开计数**（`转发=` / `改成返回=`）。第一版用明文
  `cmp x30` 比较，而 arm64e 的返回地址带 PAC 签名，比较永远不成立——
  那一版其实一直在"原样转发"，什么也没改变。掩码之后才真正生效。
- **`[0x84c098]` 这个槽有 30 处调用者**，退出函数只是其中一处。
  替身必须按调用者分流，否则会按错误的栈帧弹栈。
- **内存不是死因**：全程 62MB。
- **不是盾自己调 kill**：网关里 37 号系统调用一次都没出现，
  在 libc 的 `kill/raise/abort` 上也挂了钩，同样没有记录。

### 12.6 下一步

只剩一条路：让盾的判定通过。可用的切入点是那个 4 毫秒的窗口——
在向量被填满、开始逐项判定之前，把每个检查项对象的虚表指针换掉。


## Round 13（2026-10-28）：检测针对的是越狱环境本身，而两条退出链共用同一个闸门

### 13.1 一个此前一直没做的对照：完全不注入，App 还能不能跑

以往每一轮的"零干预基线"其实都还注入了本探针（至少接管了网关）。
这次把本项目的两份 plist 都停掉，让这个 App 得不到我们任何代码：

```
t~2s pid=[]   t~4s pid=[]   ...   t~15s pid=[]
```

**照样秒退。** 再用设备上的 Choicy 把该 App 的注入整体关掉
（`tweakInjectionDisabled`），结果一样：2 秒时就没了。

这条结论很重要：**触发检测的不是我们注入的库，而是越狱环境本身。**
所以 Round 6-8 那些"把注入库藏起来"的实验，方向从一开始就是偏的——
即使做到完美也不会有效果。改完已把 Choicy 配置按备份恢复（md5 一致）。

### 13.2 两条退出链其实共用一个闸门

原因码 4 和原因码 5 的产生点结构完全一样：

```
原因码 5：  7133d4: ldr x8,[sp,#0x90]   /  7133d8: blr x8  /  7133dc: mov x1,x0
            7133e0: mov w0,#5           /  7133e4: bl 0x40e7e4
原因码 4：  37d4c4: blr x27             /  37d4c8: mov x1,x0
            37d4cc: mov w0,#4           /  37d4d0: bl 0x40e7e4
```

两者都是"调一个回调拿到结果，然后把（原因码, 结果）交给 `0x40e7e4`"。
而 `0x40e7e4` 里真正的退出是有条件的：

```
40e7f8: mov x19, x1          ; x19 = 回调结果
40e804: cbz x19, 0x40e810    ; 结果为空 → 走退出
40e808: ldrb w8, [x19]
40e80c: cbnz w8, 0x40e848    ; *结果 != 0 → 跳过退出，转去上报
40e810: ... blr x8 ...       ; ← 真正的退出
```

**只要回调返回一个非空指针、且它的第一个字节非零，这条退出就被跳过。**
这是目前找到的唯一一个"有条件"的退出，而且它在函数边界上。
难处是两处回调都是 `blr` 寄存器调用，不改代码就够不到。

### 13.3 一个被我判断错的槽

`[0x848d70]` 是 `0x40e7e4` 里那次 `blr x8` 的目标来源，一度以为它就是退出函数指针。
按函数指针改写之后进程立刻崩——因为它不是指针本身，而是减法的一个基准：
`目标 = [0x848d70] - [某处]`。全二进制只有 5 处读它，都在退出/上报这一簇里，
将来若要动它，得把减法另一侧的槽一起算进去。

### 13.4 当前判断

把"拦退出"做到函数边界（`[0x84c098]` 那条，已生效）之后，
App 仍然是黑屏；而完全不注入时它照样秒退。两件事合起来说明：
**判定的依据在越狱环境里，且 App 的启动被这个判定卡着。**
不改代码、只改数据的手段，到这一步已经用得差不多了。

接下来要么去改代码（会撞上盾对自己 `__TEXT` 的哈希自检），
要么把 13.2 那个"结果非空即跳过退出"的闸门想办法从上流满足。


## Round 14（2026-10-28）：盾最后一步是伪装成崩溃，而且 App 到不了 RASP 那一层

### 14.1 盾的收尾动作：查环境变量，然后自己发 SIGSEGV

把 libc 的 `kill/raise/abort` 都挂上之后，启动末段的时间线是稳定的：

```
411ms  getenv("DYLD_IMAGE_SUFFIX") = (空)
456ms  libc raise: 信号 0xb   →  进程以 SIGSEGV 结束
```

所以"秒退"不是盾直接 `exit`，而是**自己 `raise(SIGSEGV)`**，
故意让它在系统看来是一次崩溃。这也解释了为什么一直找不到崩溃报告之外的东西。

顺带纠正 13.3 之前的一个判断：早前说"盾没有走 libc 的 getenv"是错的，
它确实调了，只是发生在 411ms，比我当时观察的窗口晚。

### 14.2 一个会踩的坑：整表枚举 ObjC 类会立刻招来 SIGSEGV

`objc_getClassList` 走一遍全局类表，盾会在 456ms 准时 `raise(SIGSEGV)`；
把这处枚举关掉，存活立刻回到 12 秒。可复现，两次冷启动都一样。
逐个按名字 `objc_getClass()` 则没有影响。

### 14.3 关键结论：App 根本没走到 RASP 那一层

按名字逐个查，400ms 时一个都不存在：

```
类 AppSecurityEvent 无     类 AppSecurityState 无
类 UntrustedBlockerConfiguration 无
类 JailbrokenStrategy 无   类 RASP 无
```

**这说明汇丰中国那套做法搬不过来。** 中国版的 ZDefend 是把威胁结论通过
ObjC 交给平台层，所以 hook `getAllThreats` 这类方法就能读能改；
香港这套的盾在 App 启动阶段就把结论定了，RASP 的 ObjC 层**从来没有被初始化过**，
没有任何上层对象可以 hook。

黑屏的原因也在这里：App 自己的启动流程被盾卡住，界面根本没开始搭。

### 14.4 现在的位置

| 事实 | 证据 |
|---|---|
| 不注入、乃至关掉全部注入，仍然秒退 | Round 13 的 Choicy 对照 |
| 拦退出（函数边界）后进程活 12 秒但黑屏 | Round 12 |
| 判定发生在启动早期，早于 RASP 初始化 | 本节 |
| 最终响应是 `raise(SIGSEGV)` 伪装崩溃 | 本节 |

能用"只改数据"做到的手段，到这一步已经基本用尽；
要再往前，只剩下改盾自己的代码（会撞上它对 `__TEXT` 的哈希自检），
或者去解开它那套混淆的间接调用链，直接改判定函数的返回值。
